# Delegation through Herdr

Herdr (TUI) is the default transport; this package does not require pi-subagents. These instructions are shared by research, review, architecture exploration and implementation coordination.

Herdr keeps each delegated session in its own pane on a background server, so it survives the coordinator's terminal closing. `scripts/herdr-delegate.mjs` from this package launches those sessions and writes a **run record** of what actually ran. Herdr and the helper move sessions; they do not choose work, judge results or enforce this policy.

## Preflight and launch

1. Read the project's `docs/agents/delegation.md`, and `docs/agents/delegation.json` when it exists. The JSON holds the role rows as data: harness, mode, exact model, family, tool profile and optional time limit for each role, plus the session, evidence directory, limits, worktree setup command and optional family model patterns. `node <package>/scripts/herdr-delegate.mjs config check <delegation.json>` validates it, including reviewer independence and that the table in `delegation.md` matches. Check the actual host: `config probe <delegation.json>` reports the Herdr server, the integrations for pane-based harnesses, each harness CLI and each Pi model listing; with `--live` it also sends one short, possibly charged prompt per model and compares the model that answered with the row. Without the JSON, check the same things by hand: `herdr status server` shows `status: running`, `herdr integration status` lists the integrations, `pi --list-models <pattern>` lists the model, and the Claude Code CLI is signed in. Use `herdr --help`, `herdr <command> --help` and `node <package>/scripts/herdr-delegate.mjs` for syntax; do not invent flags. Missing delegation blocks delegated work, not planning.
2. Run the coordinator inside a Herdr pane (or set `HERDR_SESSION` to the project's named session), so its `herdr` and helper commands reach the same server.
3. Select the role row. With `delegation.json`, pass `--config <its absolute path> --role <role>`: the helper takes the harness, mode, harness arguments, expected model, family and batch time limit from the row and refuses `--harness`, `--mode` or arguments after `--`, so a launch cannot silently use another model. Change the JSON, not the launch. Without it, copy the row from `delegation.md` into the launch (the manual form below). Pass the role brief from this package's `agents/` directory as a file: `--brief <absolute path>`. Herdr does not load these files; they are portable prompts, not provider configuration. Put the task (spec, ticket, base/head, allowed actions, completion contract) in its own file and pass `--task`.
4. Launch a **fresh** session, never a continuation of the implementer's conversation:
   - Implementation and research: `--mode interactive`. The helper creates the workspace (`--cwd`) or the per-ticket worktree and branch (`--worktree --repo --branch --base <immutable SHA>`), runs `herdr agent start --kind <harness>`, and submits the brief and task paths. A human can attach with `herdr agent attach <name>`.
   - Code and design review, exploration and evidence audit: `--mode batch`. The harness runs non-interactively (`pi -p --mode json`, `claude -p --output-format json`) in its own pane, and the helper writes the final answer to `--output`. The report never depends on reading the screen.
   - Model and permissions. With `--config`, the helper derives them from the row: `model` becomes `--model` (without the `anthropic/` prefix for Claude Code), and the `read-only` tool profile becomes `--tools read,grep,find,ls` for Pi or `--tools Read,Grep,Glob --permission-mode dontAsk` for Claude Code. Review, exploration and evidence-audit rows must use that profile. In the manual form, put the same harness flags after `--`. Tool flags limit the session; prompt restrictions alone are not a sandbox.
   - Read access. Claude Code in `dontAsk` mode denies reads outside its working directories, and the brief and task often live outside `--cwd` (a code review runs in the candidate worktree, its task in the original project's `.scratch/`). The helper records `readDirs` (this package's root, and the brief's and task's directories when outside `--cwd`) and passes them to Claude Code sessions as `--add-dir`. Pi receives the brief and task as `@file` attachments and needs none.
   - Where files go. The record (`--record`) goes outside the delegated checkout, or in a Git-ignored path inside it such as `.scratch/`, so the checkout stays clean. Code review, exploration and evidence-audit output follows the same rule. Design-review reports may be tracked files inside the repository (`docs/designs/reviews/…`), because `design-check` reads them from there. Research and implementation write their own artifacts. The helper refuses any other location, and refuses a record or output that already exists.
   - Use one run name per launch (Herdr agent names: a lowercase letter first, `[a-z0-9_-]`, at most 32 characters).
   - **Time limit.** Every batch run has one: `--timeout-ms` (default 30 minutes). On expiry the helper kills the harness and everything it started, and records `failed` with `failureReason: timeout`. Interactive sessions have no exit status to limit; bound them with `herdr agent wait <name> --until done --timeout <ms>` and stop the session when the wait fails.
   - **Worktree setup.** Pass the project's setup command from `docs/agents/testing.md` as `--setup "<command>"` (for example `npm ci`). It runs in the new checkout before the harness starts, with `--setup-timeout-ms` (default 10 minutes) and a log next to the record. If it fails, the harness is not started and the record says `failed` with `setup` or `setup-timeout`.
   - **Run resources.** `--ports N` finds N ports that are free at launch and passes them, with the run ID, as `MP_RUN_ID`, `MP_RUN_PORT` and `MP_RUN_PORT_1…N` to the setup command and to a batch harness; an interactive session receives them in its first prompt. The ports are not reserved: anything shared beyond a port still needs the lease that the [testing policy](TESTING.md#environment-ownership) describes.

   A complete batch launch, for the Spec axis of a code review (paths are examples):

   ```bash
   node "$MP_SKILLS/scripts/herdr-delegate.mjs" launch \
     --config "$PROJECT/docs/agents/delegation.json" --role spec-review --name spec-a2 \
     --record "$PROJECT/.scratch/import/runs/spec-a2.json" \
     --brief "$MP_SKILLS/agents/mp-review-spec.md" \
     --task "$PROJECT/.scratch/import/runs/spec-a2.task.md" \
     --output "$PROJECT/.scratch/import/runs/spec-a2.report.md" \
     --cwd "$CANDIDATE_WORKTREE"
   ```

   ```bash
   node "$MP_SKILLS/scripts/herdr-delegate.mjs" inspect "$PROJECT/.scratch/import/runs/spec-a2.json"
   ```

   The manual form of the same launch replaces `--config … --role spec-review` with `--role spec-review --harness claude --mode batch` and ends with `-- --model claude-sonnet-5-5 --tools Read,Grep,Glob --permission-mode dontAsk`; its `inspect` then needs `--expect-model anthropic/claude-sonnet-5-5`.

   Here the record and report sit in the original project's ignored `.scratch/`, outside the candidate worktree. For a worker, use `--role implementation --worktree --repo "$PROJECT" --branch ticket/a --base <integration SHA>` instead of `--cwd`, and add ports if tests need them (`--ports 1`). With `--config`, a worktree launch runs the config's `worktreeSetup` (for example `npm ci`) unless `--setup` names another command. A batch run uses the row's `timeoutMs`, else the config's `limits.batchTimeoutMs`, else 30 minutes; `--timeout-ms` changes it for one run.
5. Record the run ID (`<herdr session>:<name>:<terminal id>` in the run record), host, worktree, role, harness and the arguments; the record holds them, and for a `--config` launch also the config's path and hash. Then verify the **effective** model with `herdr-delegate.mjs inspect <record>`. It reads the model from the harness's own session file (interactive) or output stream (batch). For a `--config` launch it checks that model against the row without further flags, and against the family's model pattern when `delegation.json` has one: the output's `modelCheck` says `match`, `mismatch`, `family-mismatch`, `unknown` (a completed run reported no model), `pending` (not finished yet) or `not-applicable` (the run failed). Only `match` passes; `mismatch`, `family-mismatch` and `unknown` exit 1. For a manual launch pass `--expect-model <provider/model>`: for Pi the same value as `--model`; for Claude Code `anthropic/<id>`, so `--model claude-sonnet-5-5` is checked as `--expect-model anthropic/claude-sonnet-5-5`. Run `inspect <record>` without a flag to see the exact value. A role name, a configured argument or a worker's own statement is not verification. If inspection fails, mark independence unverified and block the review gate.
6. Research needs source search and retrieval (or direct local primary-source access for a local-only question), not specific tool names. Reviewers need read access to the target and supplied artifacts only; they never edit the candidate or run tests. The coordinator runs verification.
7. Observe completion. Interactive: `herdr agent wait <name> --until done` (do not wait for `idle`: a session that has not started yet is idle), then collect the allocated artifact. Batch: the record's `status` becomes `completed`, or `failed` with the exit code, a `failureReason` (`timeout`, `exit`, `unparsable`, `aborted`, `harness-error`, `empty`, `setup`, `setup-timeout`) and, when the harness gave one, the provider's error text as `failureDetail` (for example an invalid API key). If `inspect` reports `live.status: stale`, the run is still marked running past its limit: its process was lost (for example in a server restart), so treat it as failed. A finished process is not a passing review. Failed, cancelled, timed-out or missing output stays explicitly unresolved. Stop duplicate or stale sessions (`herdr agent list`, `herdr workspace close`) before retrying.
8. After a coordinator restart, reconcile from the run records and `herdr agent list` / `herdr pane list`: the same terminal ID is the same session. A record whose session is gone stays unresolved; do not relaunch a claimed ticket merely because the coordinator restarted.

## Independence

The project's role mapping records a **model family** (for example Claude, DeepSeek or GPT) separately from the harness (Claude Code, Pi). Both review axes must use a family different from every implementation worker that contributed to their target. The axes may use the same review family in separate fresh sessions. Never silently substitute the implementation model when a reviewer is unavailable. Derive the family from the inspected effective model, not from the harness.

Research may run concurrently. Implementation may run concurrently only in separate worktrees with safe runtime resources. A single coordinator owns tracker updates and integration merges. Workers do not recursively dispatch review or change tracker status.

## Limits

- **Verified live** with herdr 0.9.5 and pi 1.4.0 on Windows: batch Pi review (effective model read from the stream), interactive Pi worker in a new worktree, the path guards, a batch time limit that killed the run and left no orphan process, a worktree setup command receiving `MP_RUN_ID` and two free ports, a failing setup that stopped the launch, and a failed Claude Code run reported as `failed`. **Verified live on Ubuntu** (host `sen03`, pi 1.5.0, Claude Code 2.1.312): `config check` and `config probe --live` with two Claude models and one DeepSeek model (each answering model matched its row; an invalid DeepSeek key was reported with the provider's error), and a `--config` Claude Code batch review with `--tools Read,Grep,Glob --permission-mode dontAsk` that read its brief through `--add-dir`, returned its report and passed the automatic model and family check. **Not yet verified live:** an interactive Claude Code session, a `--config` interactive worker in a new worktree, and `herdr --remote` from another machine. Run the one-child check in the manual for each harness before relying on it.
- The model check passes only when **every** model the run reports matches. Claude Code's `modelUsage` can list more than one model if the CLI calls a smaller model for auxiliary work, and then the check fails even though the review model was correct. The live Claude batch runs so far reported one model. If it happens, record the reported models and treat independence as unverified. Do not weaken the check. Report it so the helper can learn to tell the main model from auxiliary ones.
- A family pattern ties a family name to model IDs (for example `^anthropic/`), so it catches a row or an effective model from another provider. It cannot tell two families served by one provider apart; the family is still the maintainer's statement.
- After `herdr server stop` or a reboot, sessions stop. Herdr restores the layout; an interactive session resumes only when its harness integration is installed (`herdr integration install pi`, `herdr integration install claude`). A batch run that was interrupted stays `running` in its record until `inspect` reports it `stale`; treat it as failed and relaunch under a new name.
- On Windows, Git Bash rewrites a leading `/` in arguments passed to native programs. The helper is unaffected; when typing `herdr agent prompt` by hand in Git Bash, set `MSYS_NO_PATHCONV=1`.
- A project-scope Pi install may not reach a worker's worktree (Herdr puts them under `~/.herdr/worktrees/`): an npm or git install lives in the untracked `.pi/npm/` tree, and a path install is recorded in `.pi/settings.json` relative to `.pi/`, so it resolves elsewhere from the worktree. Give workers this package's skill files by absolute path, or install the package at user scope; check in the worker's first output that the files were read.
